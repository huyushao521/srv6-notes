# 24 · 可观测性：IOAM、Telemetry 与策略状态

> **本章定位**：补章。第 9 章讲了 Ping/Traceroute，第 18 章讲了 SBFD。但这些都只回答"通不通"。运营最难的问题不是"通不通"，而是**"为什么这条路径今天比昨天慢了 3 ms"**。这一章讲怎么把"无信令隧道"的盲区变成可测量的数据。
>
> 一句话概括：**SRv6 省掉了逐跳信令，代价是省掉了逐跳的"心跳"**——能补上的只有两样东西：带内遥测和策略状态。

**本章要拿到的东西**：

| 问题 | 对应小节 |
|---|---|
| 三层可观测性分别看什么 | 24.1 |
| IOAM 怎么把测量信息塞进报文 | 24.2 |
| Telemetry 与 SNMP 轮询的本质差别 | 24.3 |
| SR Policy 有哪些状态值得盯 | 24.4 |
| 一次"慢 3 ms"的三步定位法 | 24.5 |

## 24.0 三层模型

```text
图 24-1：可观测性的三层

  业务层  ── 业务 SLA：时延 / 丢包 / 抖动（按 VRF、按切片）
     ▲        来源：探针、IOAM、应用侧埋点
     │
  路径层  ── SR Policy 状态：up/down、候选路径、BSID 计数、SBFD
     ▲        来源：设备 YANG / PCEP 上报
     │
  设备层  ── 接口与队列：流量、丢包、队列深度、CPU
               来源：Telemetry / SNMP
```

三层的**时间尺度不同**，这是设计监控时的核心：

| 层 | 采样周期 | 用途 |
|---|---|---|
| 设备层 | 10 s（Telemetry 可到 1 s） | 容量与故障发现 |
| 路径层 | 1 s（SBFD 更快） | 路径切换与劣化 |
| 业务层 | 分钟级 | SLA 结算与投诉举证 |

> 常见错误：**用设备层指标解释业务投诉**。接口没丢包不代表业务不慢——队列深度、路径绕远、ECMP 哈希偏移都能让设备层看起来"健康"。

## 24.1 设备层：把"看起来健康"变成可判定

:::en
Streaming telemetry provides a continuous stream of operational data from the network device to the collector, with a much lower latency than periodic polling.
:::

流式遥测从设备向采集器**持续推送**运行数据，时延远低于周期性轮询。

与 SNMP 轮询的差别不是"快一点"，而是**能不能看到瞬时峰值**：

| 维度 | SNMP 轮询（5 min） | 流式 Telemetry（10 s 或更快） |
|---|---|---|
| 微突发 | 看不到 | 可见 |
| 队列深度 | 只能看均值 | 可见峰值 |
| 计数器精度 | 采样丢失 | 连续 |
| 对设备压力 | 集中式轮询，CPU 尖峰 | 推送，压力平滑 |

必须采集的五个指标：

| 指标 | 为什么关键 |
|---|---|
| 接口丢包（出方向） | 唯一能反映"队列溢出"的指标 |
| 队列深度峰值 | 抖动的直接来源（22.4） |
| 接口利用率 P95 | 容量规划基线 |
| SRv6 转发异常计数（如无效 DA） | 压缩/映射错配的第一现场 |
| 控制面会话数（BGP/PCEP） | 控制面被攻破的信号（23.4） |

## 24.2 路径层：SR Policy 状态是新的"隧道状态"

MPLS TE 时代，隧道状态由 RSVP 信令维持，`show mpls traffic-eng tunnels` 一眼就知道。SRv6 没有信令，**必须自己去看 Policy 状态**：

| 状态项 | 含义 | 异常判读 |
|---|---|---|
| Policy operational state | up / down | down 说明候选路径不可用 |
| 候选路径状态 | active / inactive | 全部 inactive = 没有可用段列表 |
| BSID 绑定 | 已绑定 / 冲突 | 冲突会造成流量错走 |
| SBFD 状态 | up / down | down 但 Policy up = **转发面黑洞**（18.8） |
| 段列表可达性 | 每段是否在 IGP/BGP-LS 中可见 | 单段不可达 = 路径半断 |

两个高频陷阱：

1. **Policy up 但业务不通**：这是 18.8 的主题，SBFD 是唯一可靠的补充。
2. **Policy 频繁 flap**：不是设备问题，多半是算路度量抖动（22.7 案例 C 的粘性问题）。

### 24.2.1 BSID 计数：最便宜的"业务探针"

BSID 的转发计数是**零成本业务探针**：只要看 BSID 的包/字节计数，就知道这条策略上有没有真实流量。

```text
show segment-routing traffic-eng policy name PE2-URLLC detail
! 关注：BSID、policy state、candidate path、binding sid 计数
```

用它做三件事：

| 用途 | 做法 |
|---|---|
| 确认引流生效 | 配了 color 之后，BSID 计数从 0 变正 |
| 发现静默切换 | BSID 计数陡降 = 流量切走了 |
| 容量核算 | BSID 速率 × 时间 = 该切片承载量 |

## 24.3 业务层：IOAM 与探针

:::en
In-situ OAM records operational and telemetry information in the packet while the packet traverses a path, so that the information can be collected without sending additional probe packets.
:::

带内 OAM（IOAM）在报文**穿越路径的过程中**把运行与遥测信息记录进报文本身，因此**不需要额外发送探测包**。

### 24.3.1 IOAM 与探针的取舍

| 方式 | 精度 | 开销 | 适用 |
|---|---|---|---|
| 主动探针（合成流量） | 路径级，非业务级 | 额外流量 | SLA 举证、验收 |
| IOAM（带内） | 逐跳、逐业务流 | 报文变大、需芯片支持 | 疑难定位、劣化归因 |
| Telemetry（设备侧） | 设备级 | 无报文开销 | 日常监控 |

现实建议：**日常靠 Telemetry，验收靠探针，疑难靠 IOAM**。三者不是替代关系。

### 24.3.2 IOAM 的三个现实约束

1. **不是所有平台支持**，且压缩域内支持更少（19.5.2）；
2. **报文变长**，要在 MTU 预算里留位置；
3. **隐私与合规**：逐跳记录可能带出路径细节，跨域时默认关闭。

## 24.4 一次"慢 3 ms"的三步定位

```text
图 24-2：三步定位法

  Step 1  业务层：确认是全局慢还是部分慢
          ├─ 全局慢  → 进 Step 2
          └─ 部分慢  → 查 ECMP 哈希偏移 / 切片选错（走 24.5）

  Step 2  路径层：看 Policy 是否切了候选路径
          ├─ 切了    → 问"为什么切"（度量抖动、SBFD 误判）
          └─ 没切    → 进 Step 3

  Step 3  设备层：看队列深度与出向丢包
          ├─ 队列高  → 加 shaper / 调优先级（22.6）
          └─ 队列低  → 查物理（光功率、CRC、微突发）
```

配合的命令方向（示意，不同平台不同）：

| 层 | 看什么 |
|---|---|
| 业务层 | 探针 P99、抖动、丢包序列 |
| 路径层 | `show segment-routing traffic-eng policy detail`、SBFD 状态、BSID 计数趋势 |
| 设备层 | 接口 Telemetry：出向丢包、队列深度峰值、光功率 |

> 这条流程的价值不在命令，在**顺序**：先确认影响面，再看路径，最后看设备。反过来的话，你会在几十个接口计数器里迷路。

## 24.5 部分慢：ECMP 与哈希偏移

"部分慢"是 SRv6 网络里最难查的一类：同一业务，一部分用户慢、一部分正常。

| 根因 | 判据 | 处理 |
|---|---|---|
| ECMP 哈希偏移 | 慢的用户集合固定（同一 5 元组哈希） | 用 Flow Label 补熵（第 17 章） |
| 部分路径劣化 | 逐路径探针，某条 SID 列表慢 | 剔除该段/调整 Algo |
| 切片选错 | 报文的 color/DSCP 未按预期映射 | 查 BGP 扩展团体与策略匹配 |
| 压缩与非压缩混排 | 部分节点回退到 128 bit | 查 locator 格式（19.6） |

第一条最经典：**DA 相同 → 哈希相同 → 全部流量挤一条路**。SRv6 的 DA 在路径上是"有意相同"的（这正是压缩的前提），所以熵必须来自 Flow Label 或内层五元组。这是 SRv6 与 MPLS 在设计上的一个真实差异，迁移时务必确认（第 21 章）。

## 24.6 本章小结

| 记住这一条 | 为什么 |
|---|---|
| 三层时间尺度不同，不能混看 | 设备健康 ≠ 业务达标 |
| Policy 状态 + SBFD 才等于"路径活着" | 只有状态会骗人 |
| BSID 计数是零成本探针 | 一个计数器顶一套探针 |
| 压缩域内 OAM 能力下降 | 要靠 Telemetry 补 |
| "部分慢"先怀疑哈希 | DA 相同是 SRv6 的常态 |

## 实战案例

### 案例 A：Policy 一直 up，业务丢了 30%

**现象**：跨域专线丢包 30%，头端 Policy 状态 `up`，SBFD 未部署。

**排障分支**：

| 检查项 | 期望 | 实际 |
|---|---|---|
| Policy 状态 | up | up |
| SBFD | 配置了 | **未配置** |
| 段列表可达性 | 全部可达 | 中间某段 IGP 不可见 |
| BSID 计数 | 稳定 | 有值但速率波动 30% |

**根因**：中间某跳的 locator 因 IGP 汇总被隐藏（第 5 章），头端仍按旧段列表压栈，该跳按"未命中"丢弃部分报文，且不产生 ICMP。

**修复**：开 SBFD（18.8.1）+ 对 Policy 的段列表做周期可达性校验。**教训："策略 up"只代表"配置生效"，不代表"路径可用"。**

### 案例 B：升级后吞吐下降，接口计数正常

**现象**：核心升级后整体吞吐降 15%，所有接口无丢包，CPU 正常。

**期望值判定表**：

| 指标 | 升级前 | 升级后 |
|---|---|---|
| 接口出向丢包 | 0 | 0 |
| 队列深度峰值 | 30% | **78%** |
| 平均包长 | 900 B | 640 B |
| 结论 | — | 队列深度上升 → 时延上升 → TCP 降速 |

**根因**：升级引入了默认的队列策略变更，同样带宽下队列更深，时延增大导致 TCP 拥塞窗口收缩。**接口不丢包不等于没有问题**——这就是必须采队列深度的原因。

### 案例 C：只有晚上 9 点慢

**现象**：每天 21:00–23:00 部分用户慢，其他时段正常。

**判据**：

| 时段 | BSID 速率 | 队列峰值 | 慢用户占比 |
|---|---|---|---|
| 10:00 | 1.2 G | 25% | 0% |
| 21:30 | 1.3 G | **85%** | 35% |
| 22:30 | 1.3 G | 60% | 12% |

**根因**：晚间娱乐流量突增，与专线切片共用出接口队列，突发造成深度堆积；慢用户固定集合 = 哈希到同一路径。

**修复**：切片独立 shaper（22.6）+ Flow Label 补熵。**教训：容量没变、路径没变，但"共存"变了——切片的资源隔离要在压力下验收。**
