# 22 · 网络切片与确定性承载

> **本章定位**：补章。前面已经讲透了"怎么指定一条路径"（18 章）、"怎么让路径变短"（19 章）、"怎么给移动网用"（20 章）。这一章回答一个更上层的问题：**多张逻辑网跑在同一套物理网上，怎么保证互不踩踏，并且把时延 SLA 变成可交付的数字**。
>
> 一句话概括：**切片不是"多划分几个 VRF"，而是"把资源隔离做成可验证的约束"**——不能验证的隔离，只是心理安慰。

## 22.0 本章拓扑

```text
图 22-1：三切片共网（同一套物理设备，三条逻辑路径）

                     ┌──── P2 ────┐
   PE1 ──── P1 ──────┤            ├────── P4 ──── PE2
                     └──── P3 ────┘

  切片 A（eMBB，color 100）：PE1 → P1 → P2 → P4 → PE2   大带宽链路
  切片 B（URLLC，color 200）：PE1 → P1 → P3 → P4 → PE2  最短时延链路
  切片 C（mMTC，color 300）：PE1 → P1 → P3 → P4 → PE2  与 B 同路径，低优先级队列

  算法分配：
    Algo 128（min-cost，默认）  切片 C
    Algo 129（min-delay）       切片 B
    Algo 130（大带宽 + 排除 P3）切片 A

  SID：
    PE1  locator fc00:0:1::/48    BSID 池 fc00:0:1:d000::/64
    PE2  locator fc00:0:2::/48    End.DT4（VRF 9）fc00:0:2:e109::
```

| 角色 | 切片相关工作 | 容易漏的 |
|---|---|---|
| 头端 PE1 | 三条 SRv6 Policy，color 区分 | 三条策略共用同一 BSID 池要分段 |
| P 节点 | Flex-Algo 参与/排除、队列与限速 | Algo 定义不全网一致 = 路径断裂 |
| 尾端 PE2 | VPN SID、回程策略 | 回程没配策略 → 单向优秀单向烂 |
| 控制器 | 三条候选路径、SLA 度量采集 | 度量源不统一 → 算路偏差 |

## 22.1 三种隔离度：从"看起来分开"到"真的分开"

:::en
A network slice is a logical network that provides specific network capabilities and network characteristics, and that can be isolated from other slices.
:::

网络切片是一个**逻辑网络**，提供特定的网络能力与特性，并且**可以与其他切片隔离**。

"可以隔离"这三个字是全部争议的来源。业内按隔离强度分三档：

| 隔离度 | 手段 | 能防什么 | 防不住什么 |
|---|---|---|---|
| 逻辑隔离（L1） | VRF / VPN / color 区分 | 地址与路由互串 | 队列争抢、带宽挤占 |
| 资源隔离（L2） | 队列 + 限速 + Flex-Algo 路径分离 | 带宽与队列争抢 | 设备级故障、控制面过载 |
| 物理隔离（L3） | 独立设备 / 独立光纤 | 一切 | 成本 |

现网 90% 的"切片"是 L2。明确这一点很重要，因为**投标时承诺"完全隔离"、交付时给的是 L2，就是事故的起点**。

## 22.2 SRv6 做切片的四件工具

| 工具 | 作用层 | 关键配置 | 见哪一章 |
|---|---|---|---|
| Flex-Algo | 拓扑层（走哪条路） | `flex-algo 129` + 度量类型 | 第 4 章 / 22.3 |
| SR Policy + Color | 转发层（选哪条隧道） | `color 200` + 候选路径 | 第 18 章 |
| BSID | 拼接层（跨域/跨控制器） | 静态池分配 | 18.4 |
| 队列与限速 | 资源层（抢不抢得到） | QoS policy + shaper | 本节 |

前三件前文已讲，这里只补"四件工具怎么协同"：

```text
图 22-2：一次切片的完整映射

  业务标识（VRF / DSCP / 5QI）
      │
      ├─ 路由层：进哪个 VRF → 决定 End.DT4 SID
      │
      ├─ 隧道层：BGP 路由带哪个 color → 决定 SRv6 Policy（18.6.2）
      │        └─ Policy 的候选路径 → Flex-Algo 选出的 SID 列表（第 4 章）
      │
      └─ 队列层：DSCP / EXP 映射 → 出接口的哪个队列 + 多少带宽
```

四层必须**同时对齐**，任何一层漏了，SLA 就守不住。最常见的漏法是第四层：路径算得再好，出接口只有一个队列，照样互相挤。

## 22.3 Flex-Algo：五个坑里哪三个会炸

第 4 章讲过原理，这里只讲现网事故率最高的三个。

### 22.3.1 坑一：Algo 定义不全网一致

Flex-Algo 的算法定义（度量类型、亲和属性、排除规则）**必须全域网关一致**，否则同一 Algo 在不同节点算出不同拓扑：

| 现象 | 根因 | 排查命令方向 |
|---|---|---|
| 策略 up，路径在一半节点断开 | Algo 129 只在部分节点定义 | `show isis flex-algo` 逐节点比对 |
| 路径突然绕远 | 某节点 Algo 定义漏了 affinity 排除 | 比对 `flex-algo 129 affinity-map` |
| 业务全断 | 参与节点数 < 2，Algo 无可用拓扑 | 看 Algo 的 `participating` 计数 |

**自检口诀：Algo 的"三件套"（度量类型、亲和属性、参与节点）必须能在一张表里列全，列不全就是隐患。**

### 22.3.2 坑二：前缀没加入 Algo

Flex-Algo 的路径由"带该 Algo 的 Locator"构成。节点参与了 Algo，但 Locator 没带 Algo 标识，等于**该节点不在这个切片的拓扑里**：

```text
router isis CORE
 address-family ipv6 unicast
  segment-routing srv6
   locator LOC129
    algorithm 129        ! 少了这行，本节点不进 Algo 129 拓扑
```

### 22.3.3 坑三：回程没走同一切片

去程走 Algo 129（低时延），回程走默认 Algo 128（最短路）——**单向优秀**。这类问题在时延测试里表现为"P50 很好、P99 很差"，因为只有一半的流量受益。

对策：把"回程策略"写进切片交付模板，用双向探测（22.4）验收。

## 22.4 把 SLA 拆成每一跳的预算

时延 SLA 不能只写在合同里，必须拆解到"每一跳允许多少"，否则无法定位是谁超标。

### 22.4.1 一个 20 ms 端到端预算的拆法

| 组成 | 预算 | 依据 |
|---|---|---|
| 接入段（PE1 上行） | 1.0 ms | 单跳光纤 + 排队 |
| 骨干（4 跳 P 节点） | 4 × 0.35 = 1.4 ms | 每跳传播 + 转发 |
| 尾端（PE2 下行） | 1.0 ms | 单跳 |
| **排队与抖动预留** | **4.0 ms** | 峰值队列深度 × 单包时延 |
| 保护切换造成的额外时延 | 0.5 ms | TI-LFA 收敛窗口 |
| 余量（给未来增长） | 12.1 ms | 60% 余量 |

关键认知：**光传播只占预算的 10% 上下，其余都是排队**。所以"优化时延"在绝大多数情况下等于"优化队列与选路"，而不是"换更短的光纤"。

### 22.4.2 三条可验证的判据

| 判据 | 怎么测 | 达标线（举例） |
|---|---|---|
| 单向时延 | 带时间戳的探针（或 telemetry） | P99 < 10 ms |
| 抖动 | 连续探针的时延标准差 | < 1 ms |
| 丢包 | 探针序号缺口 | < 0.01% |
| 路径一致性 | 双向 traceroute / SID 列表比对 | 去回程 Algo 相同 |

> 只测 P50 的 SLA 验收，等于没验收。**必须看 P99 与抖动**，因为业务感受到的是尾部。

## 22.5 确定性网络：IP 网能做到哪一步

:::en
Deterministic networking provides a guarantee that a packet will be delivered within a bounded latency and with a bounded jitter, by reserving resources along an explicit path.
:::

确定性网络通过**沿显式路径预留资源**，保证报文在**有界时延与有界抖动**内送达。

三个"有界"分别靠什么：

| 目标 | 手段 | SRv6 里的落点 |
|---|---|---|
| 有界时延 | 显式路径 + 队列整形 | SR Policy + BSID（18 章） |
| 有界抖动 | 严格优先级队列 + 周期调度 | 出接口 QoS + 帧抢占（如支持） |
| 零丢包 | 资源预留 + 冗余路径 | PCEP 带宽预留（18.5.3）+ TI-LFA |

### 22.5.1 三个现实的边界

1. **带宽预留只有集中式算路能做**。头端 CSPF 不算带宽（18.5.2），所以"确定性"天然要求控制器在场。
2. **抖动主要由排队决定，不由路径决定**。选了一条 4 ms 的路，如果中间有 10 ms 的队列，抖动照样超标。
3. **时间同步是前置条件**。要测"有界时延"，两端时钟必须同步到微秒级；同步不准，测出来的时延毫无意义。

### 22.5.2 与工业/电力场景的衔接

| 场景 | 典型要求 | 可行的 SRv6 方案 |
|---|---|---|
| 工控（PLC） | 周期 1 ms、抖动 < 10 μs | 当前 IP 设备难以满足，需 TSN/ DetNet 专用硬件 |
| 电力差动保护 | 时延 < 10 ms、抖动 < 1 ms | Flex-Algo 硬隔离 + 严格优先级，可做 |
| 车联网 V2X | 时延 < 20 ms | SR Policy + 切片，可做 |
| 云游戏 / VoNR | 时延 < 30 ms、抖动 < 5 ms | 完全可做，性价比最高 |

**结论：SRv6 切片能稳定交付"毫秒级 + 毫秒抖动"；亚毫秒抖动要靠专用硬件，不要在标书里混为一谈。**

## 22.6 切片间防泄漏：三个必须做的检查

| 泄漏类型 | 怎么发生 | 防线 |
|---|---|---|
| 路由泄漏 | VRF 的 RT 配错，或 IGP 把 locator 泄进别的 Algo | RT 白名单 + Algo 绑定 locator |
| 资源泄漏 | 切片 A 的突发流量挤占切片 B 的队列 | 每切片独立 shaper + 严格优先级上限 |
| 控制面泄漏 | 一个切片的 BGP 会话抖动拖垮整台设备的 CPU | BGP 会话限速、独立 update-group |

最隐蔽的是第二种：**没有流量时一切正常，业务高峰时低优先级切片被饿死**。验收时必须做"压力下 SLA 复测"——这是切片交付与普通专线交付最大的区别。

## 22.7 本章小结

| 记住这一条 | 为什么 |
|---|---|
| 现网 90% 的切片是资源隔离，不是物理隔离 | 承诺与交付要对齐 |
| 四件工具必须同时对齐：路由、隧道、BSID、队列 | 缺一层 SLA 就守不住 |
| Flex-Algo 三件套全网一致 | 不全网一致 = 路径断裂 |
| 回程走同一切片 | 否则只有一半流量受益 |
| 时延预算里 90% 是排队 | "换光纤"很少是答案 |
| SLA 验收看 P99 与抖动 | P50 毫无意义 |

## 实战案例

### 案例 A：切片专线时延达标，客户仍投诉卡顿

**现象**：URLLC 切片 P99 时延 9 ms（合同 10 ms），但客户反馈视频会议卡顿。

**排障分支**：

| 检查项 | 期望 | 实际 | 判定 |
|---|---|---|---|
| 去程 Algo | 129 | 129 | 正常 |
| 回程 Algo | 129 | **128** | 不对称 |
| 抖动 | < 1 ms | 4.2 ms | 超标 |
| 出接口队列 | 独立 shaper | 与其他切片共用 | 争抢 |

**根因**：回程未配策略，走了 min-cost；同时出接口未做独立整形，高峰期与 eMBB 切片争抢队列。**时延均值好看、抖动极差**，正是"共用队列 + 单向优化"的典型指纹。

**修复**：回程配同 color 策略；出接口按切片分队列并加 shaper。

### 案例 B：Algo 129 只在三台设备上配了

**现象**：新建低时延切片上线后，业务不通，策略状态 `up`。

**期望值判定表**：

| 检查项 | 期望 | 实际 |
|---|---|---|
| 参与 Algo 129 的节点数 | 8 | 3 |
| Algo 129 的拓扑是否连通 | 是 | 否（两段断开） |
| 策略计算出的 SID 列表 | 完整 | 只到第一个断点 |

**根因**：割接脚本只推送到了部分节点。Flex-Algo 的拓扑是"参与节点的集合"，节点不足时拓扑碎片化，路径算到一半就断。

**修复**：Algo 定义纳入配置基线（与 NTP、SNMP 同级），每次变更做"参与节点数"校验。

### 案例 C：压力测试下 mMTC 切片全断

**现象**：单切片测试全部达标；三切片并跑压测时，mMTC 切片心跳丢失 80%。

**判据**：

| 指标 | 空载 | 压测 |
|---|---|---|
| eMBB 出口速率 | 2 G | 9.6 G（打满 10 G） |
| mMTC 队列丢包 | 0 | 80% |
| 严格优先级队列占比 | — | eMBB 占满 8 个队列 |

**根因**：没有为低优先级切片预留最小带宽，eMBB 突发时把队列占满，mMTC 被饿死。

**修复**：每切片配置 `bandwidth remaining ratio` + 最小保证带宽；验收流程加入"峰值并发压测"。
