23 · 攻击面与控制面加固

本章定位：补章。第 10 章讲部署时给过一节"SR Domain 加固"，但只说了"边界要过滤"。这一章把它展开成可执行的清单：SRv6 到底多了哪些攻击面、每一面怎么封、封不住的地方怎么发现。

一句话概括：SRv6 没有发明新的攻击类型，但它让"路径"变成了可写的字段——攻击者只要能让自己的包带上合法 SID，就能借你的网络走你想要的路。

本章要拿到的东西：

问题 对应小节

边界到底该过滤什么，按 SID 还是按 Block 23.2
uSID 压缩为什么让检测变难 23.1.3

23.0 攻击面全景

图 23-1：SRv6 网的四个入口

                    ┌─────────── 控制面 ───────────┐
                    │  BGP-LS（拓扑）  PCEP（路径） │
                    │  ← 被攻破：全网路径可被改写   │
                    └──────────────┬───────────────┘
                                   │
   外部域 ──[1]──> SR Domain 边界 ──┼── 内部 P 节点
   (不可信)        过滤点           │
                    └──────────────┴───────────────┘
                    ┌─────────── 数据面 ───────────┐
                    │ [2] 伪造 SRH  [3] SID 扫描    │
                    │ [4] BSID 滥用 [5] 内层欺骗    │
                    └──────────────────────────────┘
编号 攻击面 后果 主要防线
1 外部包带内部 SID 进入 借道转发、绕过策略 边界按 Block 过滤
2 伪造 SRH / 段列表 指定任意路径、绕过 ACL 入口校验 + 不解封装不放行
3 SID 扫描 摸清拓扑、找可用行为 不回 ICMP、限速、Anycast
4 BSID 滥用 白嫖 TE 路径 BSID 仅域内通告
5 内层报文欺骗 打穿 VPN 边界 uRPF + VRF 隔离

23.1 数据面的五个面

23.1.1 面一：带内部 SID 的外部包

Packets that are destined to a SID of the SR domain but originate from outside the domain must be filtered at the domain boundary.

目的地址是域内 SID、但来源在域外的报文，必须在域边界被丢弃。

这就是 RFC 8754 反复强调的"SR Domain 边界"概念。做法只有一条，且必须做：

! 边界入口方向（示意）
ipv6 access-list SRv6-INBOUND
 10 deny ipv6 any fc00:0::/32 any          ! 禁止外部包目的地址落在 Block 内
 20 permit ipv6 any any
!
interface HundredGigE0/0/0/0
 ipv6 access-group SRv6-INBOUND ingress

三个容易漏的方向：

漏法 后果
只做了 PE 侧入口，没做对等互联（IX/上游） 上游注入的 SID 目的包直穿核心
只做 ingress，没做 egress 内部被攻陷的机器可向外发 SID 目的包做反射
只封 Block，没封 BSID 池 BSID 段被外部直接使用（23.1.4）

23.1.2 面二：伪造 SRH

SRH 本身没有认证字段。攻击者若能构造带 SRH 的包并送入域内，就能指定路径。防线不是"检测 SRH"，而是不让带 SRH 的包从边界进来：

! 更严格的做法：边界不允许任何携带 SRH 的入向报文
ipv6 access-list SRv6-NO-SRH
 10 deny ipv6 any any srh            ! 平台支持按扩展头匹配时使用
 20 permit ipv6 any any

平台不支持匹配扩展头时，退而求其次：边界按"目的地址必须是域外前缀"白名单，而不是黑名单。

23.1.3 面三：uSID 让检测变难

这是第 19 章的副作用，在安全上很致命：

特征 未压缩（SRH） 压缩（uSID）
是否带 SRH 带 常常不带
检测手段 看 SRH 存在与否 无法从头部判断
路径信息 明文可见 编码在 DA 的 16 bit 段里
防火墙可读性 可读段列表 只能读到 Block

后果：如果安全设备依赖"有 SRH 就拦"，压缩后这个判据直接失效。务实的替代是把判据换成"DA 属于 Block 且来源不在域内"——与 23.1.1 合并成一条规则。

23.1.4 面四：BSID 滥用

BSID 是"隧道的名字"，谁能让包的目的地址等于 BSID，谁就能白嫖这条 TE 路径（含带宽预留）。

防线 做法
不向域外通告 BSID BGP-LS 的 BSID 属性只域内传递
边界封 BSID 池 与 Block 一起加进 ingress ACL
BSID 池与 locator 分开规划 便于单独写规则（10 章的地址规划）
按 BSID 做速率限制 头端对 BSID 目的流量限速

23.1.5 面五：内层欺骗打穿 VPN

SRv6 的 VPN 隔离靠"内层地址 + VRF"。若攻击者能构造"外层合法 SID + 内层伪造源地址"的包，就可能命中别人的 VRF（取决于实现是否有源校验）。

防线三条，缺一不可：

  1. VRF 内 uRPF（严格模式或宽松模式，按业务选）；
  2. End.DT 行为前做内层源地址合法性检查（部分平台默认关闭，需显式开）；
  3. 对 CE 侧做前缀白名单（只允许该 VRF 声明的内层前缀）。

23.2 边界过滤清单（可直接抄）

方向 过滤内容 动作
入向（对等互联） 目的地址 ∈ 本域 Block deny
入向（对等互联） 目的地址 ∈ BSID 池 deny
入向（对等互联） 携带 SRH deny（平台支持时）
入向（CE 接入） 源地址不在该 CE 声明前缀内 deny
出向（对 CE） 目的地址 ∈ Block 或 BSID 池 deny
域内（P 节点之间） 不做 SID 过滤（性能优先），靠边界 permit

一句话：过滤只做在边界，核心不做。核心加 ACL 会直接把 SRv6 的"无状态转发"优势砍掉一半。

23.3 控制面：比数据面更值得担心

The PCE and the PCC must authenticate each other before any stateful PCEP message is exchanged, since a forged update can redirect traffic to any path chosen by the attacker.

PCE 与 PCC 在交换任何有状态 PCEP 消息之前必须相互认证，因为一条伪造的更新就能把流量重定向到攻击者选定的任意路径。

数据面被攻破，影响一条路径；控制面被攻破，影响全网路径。

面 攻击方式 后果 加固
BGP-LS 伪造 LSP / 注入假节点 控制器算出通往黑洞的路径 TCP-AO / MD5、邻居白名单、只收可信发言人
PCEP 未授权 PCUpd 下发策略 头端被指到任意路径 TCP-MD5 / TLS、会话白名单、delegation 权限
控制器 凭据泄露 全网策略被改写 RBAC、双人复核、变更审计
gNMI/Telemetry 未授权读取拓扑 信息泄露 TLS + 证书、只读账号

PCEP 的风险最容易被低估：一个有 PCEP 会话的节点可以直接给头端下发任意 SID 列表，等于拥有该头端的转发控制权。

! PCEP 加固示意
pce
 address ipv6 fc00:0:99::1
 !
!
segment-routing
 traffic-eng
  pcep
   ! 启用 TCP-MD5（关键字随版本变化）
   !
  !
 !
!

三条硬要求：

  1. PCEP 会话只允许来自两个控制器 IP（主备），其他一律拒绝；
  2. 控制器与设备之间的证书/密钥走独立管理网，不走业务网；
  3. 策略变更留审计：谁在什么时候把哪条策略改成了什么。

23.4 出事后从哪看：五个计数器

现象 看什么 判读
边界 ACL 大量命中 ingress ACL 计数 有人在扫 SID 或误配
域内出现奇怪路径 节点 DA 缓存 / 转发计数 有伪造 SRH 的包
BSID 流量异常 BSID 计数（一般按 Policy 统计） 有人白嫖 TE 路径
控制器算路异常 BGP-LS 拓扑节点数 有假节点注入
策略被批量改写 变更日志 / PCEP 会话数 控制面被攻破

23.5 本章小结

记住这一条 为什么
边界按 Block + BSID 池过滤，核心不过滤 兼顾安全与性能
压缩后"看 SRH"的判据失效 换成"DA ∈ Block 且来源域外"
控制面风险 > 数据面风险 一个 PCEP 会话等于转发控制权
BSID 只在域内通告 否则带宽白送
内层欺骗靠 uRPF + 前缀白名单 三层缺一不可

实战案例

案例 A：上游注入 SID 目的流量，核心成为放大器

现象：核心链路某方向流量突增 40%，且目的地址集中在 locator 段；业务本身无异常。

排障分支：

检查项 期望 实际
边界 ingress ACL 是否存在 有 无（只有 egress）
异常流量的目的地址 域外 fc00:0:3::/48 内的 End.X
源头 域内 上游某客户
出口 域内 疑似反射到另一个域

根因：边界只做了出向过滤，入向未封 Block，外部客户可用域内 End.X SID 让核心帮忙转发。

修复：补入向 ACL（23.2 清单第一行），并对上游做源地址校验。教训：ACL 只写一半等于没写。

案例 B：PCEP 会话被冒用，策略集体偏离

现象：多条 SRv6 Policy 的 SID 列表同时变化，业务时延整体劣化，无配置变更记录。

期望值判定表：

检查项 期望 实际
PCEP 会话数 2（主备） 3
新会话来源 控制器管理地址 一个业务网段地址
会话认证 MD5/TLS 开启 未开启
策略变更日志 有记录 无（来自非控制器源）

根因：PCEP 未开认证且允许任意源建会话，攻击者用一条 PCUpd 把多个头端的策略改到劣质路径。

修复：PCEP 会话白名单 + MD5/TLS + 变更审计。教训：PCEP 的开放程度按"等同 SSH"对待，不要按"内部协议"对待。

案例 C：压缩上线后 DDoS 清洗失效

现象：压缩域上线后，清洗中心的按 SID 分流规则失效，攻击流量直接打穿到目标。

判据：

项 上线前 上线后
报文含 SRH 是 否（全压缩）
清洗规则匹配字段 SRH 段列表 匹配不到
DA 可见信息 完整 SID 列表 仅 Block + 微指令

修复：清洗策略改按 Block + 微指令区间 + Flow Label 组合分流；必要时在清洗中心前保留一段非压缩域作为"可观测边界"。教训：安全架构要跟着封装形态一起改，不能只改转发面。
