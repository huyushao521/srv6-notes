19 · 头压缩工程化：uSID、NEXT-CSID 与 REPLACE-CSID

本章定位：补章。第 2 章讲过"uSID 一个 16 bit 段就是一条微指令，6 条以内不用 SRH"，但只讲了是什么。这一章回答三个现网一定会撞上的问题：SID 列表超过 6 条怎么办、压缩之后 OAM 还看不看得见、压缩之后 ACL 和 TE 还对不对。英文块为 RFC 8754 / RFC 8986 及压缩草案的规范性语句摘录（逐字原文以 IETF 正文为准），中文为工程解读。

一句话概括：压缩省下的不是带宽，是芯片查表次数和 MTU 预算；付出的代价是——你再也数不清报文里到底走了几跳。

本章要拿到的东西：

问题 对应小节
一条 10 跳的 SRv6 路径，到底多花多少字节 19.1
3216 的 6 个槽位满了，第 7 跳怎么写 19.2 / 19.3
NEXT-CSID 和 REPLACE-CSID 差在哪，能不能混跑 19.3 / 19.4
压缩后 TE 的 SID list、BSID、PCEP 有什么变化 19.5.1
压缩后 traceroute 怎么定位到具体某一跳 19.5.2
压缩域与未压缩域在哪里转换，谁能转 19.6
为什么说压缩是"芯片友好"而不是"省带宽" 19.7

19.0 本章拓扑

图 19-1：压缩对比场景（同一张 8 跳网络，两种编码）

  未压缩（128 bit/SID，必带 SRH）：
  PE1 ── P1 ── P2 ── P3 ── P4 ── P5 ── P6 ── PE2
   每跳一个 128 bit SID → SRH = 8 + 16×8 = 136 字节

  压缩（uSID / NEXT-CSID，32 bit Block + 16 bit/段）：
  PE1 ── P1 ── P2 ── P3 ── P4 ── P5 ── P6 ── PE2
   8 跳 = 8×16 bit = 128 bit = 一个 128 bit 容器装得下
   → 不需要 SRH，DA 就是整条路径

  SID 取值（沿用本站约定）：
    Block          fc00:0000::/32
    PE1 微指令 0001   P1 微指令 0011   P2 微指令 0012
    P3  微指令 0013   P4 微指令 0014   P5 微指令 0015
    P6  微指令 0016   PE2 微指令 0002 + 功能 e000（End.DT4）
角色 压缩相关配置 说明
PE1（头端） locator 指定 usid 格式；SRv6 Policy 段列表 决定压不压
P1–P6 locator 带微指令；unode psp-usd 行为 决定能不能压
PE2（尾端） 压缩 locator + VPN SID 必须能解出最后一段
边界节点 同时通告压缩与非压缩 locator 19.6 的转换点

19.1 先算账：一条 SID list 到底多占多少字节

The Segment Routing Header (SRH) is used to encode an ordered list of segments. The Segment List is encoded in reverse order, with the last element of the path being the first element of the list.

SRH 用来编码一份有序的段列表，且列表是倒序存储的：路径的最后一跳在列表第 0 位。这和 MPLS 标签栈的语义完全一致——都是"栈顶即下一跳"，所以从标签栈迁移过来的工程师第一眼就能对上。

19.1.1 SRH 的固定成本

一个 SRH 的固定开销是 8 字节头 + 16 字节/SID：

组成 长度 内容
Next Header 1 B 通常是 41（IPv6）或 4（IPv4）
Hdr Ext Len 1 B 以 8 字节为单位
Routing Type 1 B 4 = SRH
Segments Left 1 B 还剩几个段要处理
Last Entry 1 B 列表最后一个元素的下标
Flags 1 B 含 P（保护）位、O（OAM）位
Tag 2 B 可用于引流/分组
Segment List[0..n] 16 B × n 每个 128 bit SID

对一个 10 跳的显式路径，n = 10，SRH 占 8 + 160 = 168 字节。加上 IPv6 头 40 字节，转发面上已经是 208 字节的头。

19.1.2 边际成本才是要命的

单看一次不吓人，要命的是它每包都要处理：

场景 无压缩 压缩（uSID） 差额
10 跳 TE 隧道，内层 100 B 语音包 40 + 168 + 100 = 308 B 40 + 100 = 140 B -55%
同上，内层 1200 B 视频包 1408 B 1240 B -12%
转发芯片每包处理次数 每跳读 SRH 并改写 SL DA 不动，只做最长匹配 -1 次查表/跳

两个结论：

  1. 小包受害最重。语音、游戏、工控、5G 信令都是小包，压缩收益集中在这些业务上；大包收益有限，但 MTU 预算收益仍然实在——1500 的链路少压 128 字节 SRH，就少一批分片。
  2. 真正的收益在芯片。每跳少读一次 SRH、少算一次 SL 递减，是转发面指令数的减少，不只是带宽。19.7 展开。

一句话：压缩不是为省带宽设计的，是为"让 6 跳以内的路径变成一次普通 IPv6 最长匹配"设计的。

19.2 uSID 3216：把 6 条微指令塞进一个 128 bit

A uSID is a 16-bit segment identifier. A uSID carrier is a 128-bit container that can carry a 32-bit block and up to six 16-bit uSIDs.

uSID（micro-SID）是一个 16 bit 的段标识；一个"载体"是 128 bit 容器，可装 1 个 32 bit Block + 最多 6 个 16 bit uSID。

19.2.1 结构

图 19-2：3216 的位布局

  bit  0                                                        127
       ┌──────────────┬────────┬────────┬────────┬────────┬────────┬────────┐
       │  Block (32)  │ uSID 1 │ uSID 2 │ uSID 3 │ uSID 4 │ uSID 5 │ uSID 6 │
       │              │  (16)  │  (16)  │  (16)  │  (16)  │  (16)  │  (16)  │
       └──────────────┴────────┴────────┴────────┴────────┴────────┴────────┘
        fc00:0000     0001     0011     0012     0013     0014     0015

  PE1 发出的报文 DA 就是上面这整个 128 bit：
    一次最长匹配 → 命中 Block fc00:0000::/32 → 执行 0001 → 前移，露出 0011

地址规划上，Block 全网唯一，微指令在 Block 内唯一。这就是第 10 章反复强调地址层级的原因——压缩方案把"地址规划"变成了"路径编码"，规划错了压缩就没法用。

19.2.2 shift-and-forward：一层位运算

节点收到 DA 后的动作固定为四步（RFC 8986 的 uN/uA 行为族）：

  1. 用 Block 做最长匹配，确认这包是给我的；
  2. 取当前要执行的那一段（16 bit），查微指令表；
  3. 把这一段处理完，后面的段整体前移 16 bit；
  4. 转发到该微指令绑定的出接口/下一跳。
图 19-3：P1 上的移位

  进：  fc00:0000:0001:0011:0012:0013:0014:0015
                     ↑ 当前段（P1 执行 0011）
  出：  fc00:0000:0011:0012:0013:0014:0015:0000
                   ↑ 前移 16 bit

工程上要抓住三点：

  • 没有 SRH 时"还剩几段"存在哪：各家实现不同（有靠末段是否为零判断、有靠本地表项），排障时不要假设一定能抓到 SRH 看进度。
  • Block 不变。整条路径始终在同一 Block 内移动，所以跨 Block（跨域、跨运营商）必须换封装或解封装。
  • 末段必须落在本机 Locator。6 段之后还有路，就得靠 SRH 或重新压栈。

19.3 NEXT-CSID：uSID 的标准形式

Compressed SIDs are carried in the Segment List. When a compressed SID is processed, the next compressed SID is moved into the position of the current one, and processing continues with the same Destination Address format.

压缩 SID 放在 Segment List 里；处理完一个压缩 SID 后，下一个压缩 SID 被移到当前位置，报文继续按相同的 DA 格式处理。

19.3.1 术语对齐

NEXT-CSID 就是把厂商私有叫法"uSID"标准化之后的说法。互操作的第一道坎就是这张表：

私有叫法 标准叫法 含义
uSID CSID（Compressed SID） 16 bit 压缩段
uSID carrier CSID container 128 bit 载体，装 6 个 CSID
unode / uA / uN End with NEXT-CSID behavior 压缩段的行为族
3216 Block 32 bit + CSID 16 bit × 6 同构

A 厂商文档写 uSID、B 厂商写 CSID，测试时以为要两套配置，其实是一回事。

19.3.2 超过 6 段怎么办

这是现网最常被问的问题。答案不是"压缩支持任意长度"，而是压缩只覆盖一段连续区间：

图 19-4：9 段路径的编码（6 段压缩 + 3 段普通）

  SRH Segment List（倒序）：
    [0] fc00:0:2:e000::                    ← 尾端 End.DT4（128 bit，不压）
    [1] fc00:0:16:0016::                   ← P6 的 End（128 bit）
    [2] fc00:0:15:0015::                   ← P5 的 End（128 bit）
    [3] fc00:0000:0001:0011:0012:0013::    ← 一个容器装 4 个 CSID
  SL = 3

  头端压栈顺序：先压未压缩段，再压压缩容器；出包时 DA = 容器。
  容器内段用完后，SL 减 1，切到下一个 128 bit 段。

要点：

  • 压缩容器本身是一个 128 bit 段，它占 SRH 里一个位置，内部装最多 6 条微指令；
  • 因此 SRH 长度按 128 bit 段计，不按微指令计：10 跳路径若 6 跳可压，SRH 只需 8 + 16×5；
  • 压缩是逐段决定的，不是整条策略一刀切。路径尾部常跨 Block（VPN SID 在另一个 Block），那几段就保持 128 bit。

一句话：压缩解决的是"同 Block 内长路径"，跨 Block 的部分老实写 128 bit。

19.4 REPLACE-CSID：另一种压缩思路

In the REPLACE-CSID encoding, the current compressed SID is replaced by the next compressed SID in the same container, without shifting the container.

REPLACE-CSID 的做法是替换：当前压缩 SID 被容器里的下一个压缩 SID 直接覆盖，容器内其他位置不动。

19.4.1 两种算法的差异

维度 NEXT-CSID REPLACE-CSID
递进方式 后续段整体前移 16 bit 当前位置被下一段覆盖
剩余长度信息 由 DA 内容/本地状态推断 明确定义在容器内的固定位置
参数（Arg）携带 压缩后 Arg 空间紧张 有专门位置放长度与参数
芯片实现 一次移位，逻辑简单 读改写同一容器，逻辑稍复杂
互通现状 主流，厂商大规模支持 支持面窄，特定场景使用

19.4.2 能不能混跑

同一条 SRv6 Policy 的同一个容器内不能混用。判断方法很朴素：

  • 看头端 locator 格式：3216 / usid-f3216 属于 NEXT-CSID 家族；
  • 看设备是否声明支持 REPLACE-CSID（多在 Release Notes 里，不在配置里）；
  • 两端不一致时，结果只有两种：退化成不压缩，或直接不通。

排障信号：策略 up、业务通、但 traceroute 全部超时 —— 先查这一条。

19.5 压缩打翻的三样东西

这一节是本章最该记住的部分。压缩不是纯收益，它会反向影响已有功能。

19.5.1 对 TE：段列表变短，算路反而更难

影响点 现象 处理办法
PCEP 段列表 控制器下发的 ERO 里压缩段与普通段混排 控制器需知道头端 Block 与 locator 格式，否则头端编不出来
BSID 不变，仍是 128 bit BSID 必须落在头端本机 Block 内
ECMP 熵 压缩后 DA 可变位少 靠 Flow Label 补熵（第 17 章），不要把熵压在 DA 上
严格显式路径长度 单容器最多 6 段 超过 6 跳必须回退 SRH，容量账要重算
跨域 Block 不同 域边界换封装，或用 BSID 拼接（18.9）

头端要显式声明格式（IOS XR 示意，不同版本关键字有差异）：

segment-routing
 srv6
  locator MAIN
   micro-segment behavior unode psp-usd
  !
  locator MAIN-3216
   format usid-f3216
  !
 !
!

双 locator 是推荐做法：一个 3216 压缩 locator 用于域内长路径，一个普通 locator 用于跨域与第三方互通。两个都通告进 IGP，靠算法或度量区分使用场景。

19.5.2 对 OAM：traceroute 为什么看不见中间跳

这是压缩带来的最大运维坑。传统 traceroute 依赖"TTL 递减 + 每跳回 ICMP"，压缩路径上：

  • DA 在中转节点被就地改写，源端看到的 DA 序列不反映跳数；
  • 没有 SRH 时，中间节点没有可读的"第几跳"字段；
  • 回程 ICMP 可能带着已改写的 DA 回来，源端无法反推。

三种可行的定位手段：

手段 做法 局限
带 SRH 的探测 强制探测报文带 SRH（O 位），逐段 ping 只覆盖 128 bit 段，容器内微指令要单独探
逐段 ping 微指令 直接 ping fc00:0000:0011:: 逐个微指令地址 次数等于段数，必须脚本化
数据面遥测 Telemetry / SBFD 反推（第 24 章） 需设备支持，不能替代一次性定位

实操建议：压缩域内不要指望一条 traceroute 走天下，把"逐微指令 ping"做进巡检脚本，比事后排障便宜一个数量级。

19.5.3 对业务 SID：压缩只发生在路径中段

压缩 locator 里的微指令只能表示转发路径，不能承载业务语义（VPN、L2、UPA）。所以一条完整的业务路径尾巴长这样：

图 19-5：压缩路径 + 非压缩业务 SID

  DA 序列：
    fc00:0000:0001:0011:0012:0013::   ← 压缩容器：PE1→P1→P2→P3
    fc00:0:2:e109::                   ← PE2 的 End.DT4（VRF 9），128 bit

结论：End.DT4/DT6/DX2 这些业务行为始终是 128 bit 段，压缩省的是它们前面那段"怎么走"，不是"到了干什么"。混写会得到两类错误：

  • 把业务 SID 编进微指令 → 设备认为它是转发段，业务查表命中不了，静默丢包；
  • 把转发段写成 128 bit 混进压缩容器 → 容器内 6 个槽位的边界算错，第 4 段之后全乱。

19.5.4 对安全与 ACL：SRH 没了，规则匹配什么

传统做法 压缩后是否可行 替代方案
匹配 SRH 里的段列表做路径准入 不行（可能完全没有 SRH） 匹配 DA 的 Block 前缀 + 微指令区间
按 SID 做 uRPF 部分可行 按 Block 做 uRPF，微指令区间做 ACL
DDoS 按目的 SID 分流清洗 需改造 按 Block + Flow Label 抽样
防火墙看内层载荷 不受影响 见第 12 章 SR-aware

第 10 章的 SR Domain 边界过滤在压缩域里必须改成"按 Block 白名单"，因为逐 SID 名单在压缩后不可枚举（微指令是 16 bit，全空间 65536 个）。

19.6 互通：压缩域与未压缩域的边界

Nodes that do not support compressed SID processing will treat the compressed SID as an ordinary 128-bit SID and fail to process the remaining compressed SIDs in the container.

不支持压缩 SID 处理的节点，会把压缩 SID 当作普通 128 bit SID —— 于是容器内剩下的微指令全部丢失。

这句话解释了压缩域最常见的故障形态：报文到了边界节点，业务不通，但没有任何告警。

19.6.1 转换点在哪

图 19-6：压缩域 → 普通域

   压缩域（Block fc00:0000::/32）        普通域
   PE1 ── P1 ── P2 ──[BR]──────────────── PE2
                       │
                     边界路由器 BR：
                       1. 认出 DA 属于压缩 Block
                       2. 取出容器内剩余微指令
                       3. 重新压栈成 128 bit 段列表（带 SRH）
                       4. 转入普通域

三种落地方式，按改造量排序：

方式 做法 适用
边界双栈 BR 同时支持两种 locator，做压栈转换 首选，改造集中在一个节点
分段串接 压缩 Policy 到 BR 结束，BR 再起一条 Policy 接第二段 不动协议，纯策略拼接（18.9 的 BSID 拼接）
全程不压 跨域段直接用 128 bit 最简单，代价是放弃收益

19.6.2 能力通告要看清的两位

信息 在哪看 排障含义
SRv6 Capabilities 的 O 位 BGP-LS 属性 TLV（18.2.2） O 位=1 表示支持 OAM，不等于支持压缩
压缩支持 各厂商 release note / capability TLV 的私有位 没有统一标准位，必须查文档
locator 格式 IGP 里的 Locator TLV / 本机配置 3216 与非 3216 一眼可分

一句话：压缩能力没有标准化的"我支持"标志位，所以跨厂商组网时，压缩只在"自己完全掌控的域内"开启，跨域一律走 128 bit。

19.7 硬件视角：为什么压缩是"芯片友好"

同一个 8 跳路径，两种编码在转发芯片上的动作数量完全不同：

每包每跳动作 无压缩（SRH） 压缩（CSID）
读 IPv6 头 1 1
读扩展头链 1（找 SRH） 0
SL 递减与回写 1 0
DA 替换（取下一 SID） 1（写 16 B） 1（移位 16 bit）
查表 1（128 bit 最长匹配） 1（Block 匹配 + 微指令表）
表项规模 每 SID 一条 每微指令一条 + Block 汇总

三点工程含义：

  1. 表项规模可控。128 bit SID 全局唯一，运营商动辄几十万条；微指令只需要"Block 汇总 + 每节点少量微指令"，规模从 O(节点数) 降到 O(Block 数 + 微指令数)。
  2. 读写带宽省。SRH 改写要回写 16 字节，是内存带宽的实打实消耗；移位只动 DA 的 16 bit 窗口。
  3. 但功能受限于芯片。不是所有平台都能做 16 bit 移位；能不能开压缩，最终由线卡型号 + 微码版本决定，跟"配置支不支持"是两件事。

排障经验：升级后策略不生效，先确认线卡是否支持微指令行为，而不是先查配置。同一个机箱里不同线卡能力不同是常态。

19.8 本章小结

记住这一条 为什么
压缩省的是芯片动作与 MTU，不是"带宽" 大包收益只有 10% 量级，小包才有 50%
一个容器 6 段，超了就回退 SRH 长路径是"压缩 + 128 bit 混排"，不是纯压缩
业务 SID 永远是 128 bit 压缩只管"怎么走"，不管"到了干什么"
NEXT-CSID 与 REPLACE-CSID 不混跑 混跑表现是"策略 up、业务通、traceroute 全超时"
压缩域内 traceroute 不可靠 必须改用逐微指令 ping 或遥测
跨厂商/跨域不开压缩 没有标准能力位，靠文档与实测

实战案例

案例 A：第 7 跳之后业务全断

现象：新开的跨省专线，域内 6 跳、域间 3 跳，共 9 跳。域内业务正常，跨域后完全不通，两端 PE 的 SRv6 Policy 状态均 up。

排障分支：

检查项 命令/位置 期望值 实际值
头端 Policy 段列表 show segment-routing traffic-eng policy name X 9 段 9 段（1 容器 + 3 段）
域边界节点是否支持压缩 线卡能力 支持 不支持
边界节点收到的 DA show cef ipv6 <DA> 命中容器 命中普通前缀，剩余段丢失
尾端是否收到报文 接口计数 增长 不增长

根因：头端把 9 跳路径压成"1 容器 + 3 段"，容器内 4 条微指令在边界节点不被识别，剩余段被整体丢弃，且不产生 ICMP（因为 DA 匹配成功、只是微指令未命中）。

修复：边界双 locator + 压栈转换；或策略在边界拆成两段（BSID 拼接）。结论：压缩只在同厂商域内开，跨域显式改回 128 bit。

案例 B：traceroute 全部超时，但业务好得很

现象：压缩域上线后，网管巡检脚本报"路径不可达"，业务监控一切正常。

期望值判定表：

探测方式 压缩域内的期望结果
traceroute 默认（无 SRH） 中间跳大面积超时，属正常
traceroute 带 SRH + O 位 只能看到 128 bit 段边界
逐微指令 ping fc00:0000:00NN:: 每跳应有回包
逐微指令 traceroute 可定位到具体微指令

修复：把巡检脚本从"traceroute 通不通"改成"逐微指令 ping 是否全绿"，并把该项写进上线检查单。这是流程问题，不是设备问题。

案例 C：安全设备看不到 SRH，策略失效

现象：数据中心入口的 ACL 依赖"匹配 SRH 段列表"识别跨域路径，压缩上线后全部失效，等于门户大开。

分支判断：

报文里还有 SRH 吗？
├─ 有（跨 Block 段）→ ACL 仍可用，但只覆盖部分路径
└─ 没有（全压缩）  → 必须改规则
      ├─ 改匹配 DA Block 前缀（推荐，规则数少）
      ├─ 改匹配 Flow Label 分组（需端到端一致）
      └─ 改 SR-aware 防火墙看内层（第 12 章，改造成本最高）

教训：压缩是转发面改造，但会连带打穿安全面假设。上线前必须把"依赖 SRH 的规则清单"过一遍。
